## 签发契约

客户端只描述工具、精确版本、显式项目与所选复用实例；不提交命令、argv、环境变量或自由步骤图。
Recipe 分支先校验版本、工具集合、重复项、精确版本和路径预算，再读取环境、查询清单或探测管理器。
最大两个工具项；范围、别名、重复工具、冲突版本、未知声明和不支持的作用域拒绝签发可执行计划。

Node 和 Python 都需对请求版本本身进行项目声明匹配，再考虑已有实例或安装。Node 需抽出可用于纯请求版本的声明匹配入口，不能依赖已有候选；冲突或未知声明保持拒绝，不能只检查 Python 项目要求。

父计划绑定每个工具的 request ID/generation、mise 原生包与平台、精确版本、项目规范路径、配置文件指纹、
项目声明证据，以及允许修改的 `tools.node` / `tools.python` 字段。首切片拒绝以项目目标别名写入全局/HOME 配置、隐式迁移旧 `.tool-versions` 或 Node/Python 各自落到不同配置目标；相关配置路径需冻结并重新核定。缺失清单、活动扫描或 journal 故障不能获得执行资格。
父计划使用现有 120 秒短期单次批准规则；执行命令只接受后端签发的父 plan ID。已开始的安装不因批准到期中止，但后续新的配置变更仍需检查到期。安装最长可达 900 秒，若绑定前已过期，只做清理并记录实际安装残留，显式重签未完成项；内部不延长批准。

`reuse` 不等于可绑定。只读报告目前可选择其他渠道的健康候选；新执行入口必须核定 mise/runtime/macOS 身份、
健康与新鲜状态、精确版本和具体绑定能力。多个候选无法唯一确定时要求显式选择，不依据列表顺序决定写目标。
安装尚未完成时批准来源、版本和配置目标，实际安装 ID/locator 留到重扫后取得，不能由前端补填。两工具共用冻结后的规范项目与配置目标；阶段不能重新从 cwd 或环境变量选择另一个写目标。

已有项目选择已是所请求的精确版本时，走无变更核对：实际解析仍须指向批准的实例。验证通过可以记录已满足，不能因 `already exact` 错误再改写配置，也不能把外部已有选择登记为本次新建绑定收据。解析不匹配时仍须停止。

只读 `recipe_preview` 继续使用临时预览会话，不签发或缓存执行批准，也不淘汰用户已打开的独立计划。

## 单父任务与阶段承接

父任务一次获得应用级写权限，贯穿所有工具项，沿用父 ID 的取消状态和日志。内部阶段不能再次调用公开的
`operation_execute`，也不能在锁间隙让另一项 Z.Env 写任务进入。阶段驱动继续复用原有来源、配置、文件和写前校验。父任务只持应用级写 Guard；普通 query lease 由每个阶段按工具/provider 顺序申请并释放，不能先持有父 QueryLease 再嵌套申请子 lease。

每个工具项依次完成：

1. 核对父计划批准范围与当前证据；已有候选必须重新核定，缺失版本才执行批准的 mise 精确安装。
2. 重扫来源并取得实际实例；版本、provider/package、平台、路径、健康或覆盖不匹配时停止。
3. 在父计划允许的项目/字段范围内物化绑定步骤，再次核对声明和文件指纹。
4. 写入项目选择，重扫并核对受控运行时版本、实际解析路径与绑定收据，之后才能把该项标为完成。

每次查询用固定长度父 nonce、工具项索引、阶段和扫描序号构造有界唯一 ID，沿用 query 校验。
不能重复使用 `mutation-{id}`、`python-mutation-{id}` 或只按父 ID 编号的 refresh 请求。

安装、绑定和重扫会改变自身的清单/config 证据，不能提前签一批子计划后直接依次执行。
后续阶段只能承接本父任务自己提交并核验的快照与变更，保留更新后的配置期望指纹；外部刷新造成 generation/request ID 变化仍需停止，不能把任意最新缓存当作自身扫描结果。不能通过读取最新文件再自动重签来接受外部修改。
两工具共用项目配置时，第二项的差异与备份以第一项已成功后的状态为基线，保留此前成功选择和无关字段。

## 复用补偿前的修正

审查发现旧 Python Bind rollback 仅核对 Python 字段后恢复整个旧文件，可能覆盖外部对其他字段的修改；收据清理失败也会被吞掉。这些不能直接作为安全配方补偿复用，先按 [补偿安全修正](./python-compensation-safety-2026-11-07.md) 核对完整写后状态和实际清理结果。

Python 绑定与补偿还需阶段 query lease；必要写后/补偿扫描必须隔离 query/probe 取消 token，而非仅清除线程 CURRENT。纯验证扫描仍可取消。解析核对若在取消时已开始，可完成只读核对，但不再开始下一个工具项或新的变更步骤。

## 失败、取消与持久记录

| 情况 | 必须保留的结果与恢复边界 |
| --- | --- |
| 安装成功、绑定失败 | 保留安装与下载/缓存结果；补偿该失败项仍归自己所有的配置变化；重新扫描后重签未完成项 |
| 第一项成功、第二项失败 | 第一项保持完成；第二项记录实际残留；不恢复整个配方开始前的项目配置 |
| 外部改写或补偿冲突 | 停止后续写入，保留外部修改、收据和备份，明确报告冲突 |
| 用户取消 | 停止新的变更步骤；写入后的核对和必要补偿仍完成，记录真实残留 |
| journal 故障或执行恐慌 | 不继续写入；按可获得的证据记录中断并进行必要清理 |
| 重启 | Running 父任务/阶段标记中断；不自动安装、绑定或重放计划 |
| 显式重试 | 全部相关证据重新读取；只重新批准失败和未执行项，不自动重做此前成功项 |

配方记录使用明确的 Recipe 身份和工具项/阶段状态，历史列表继续兼容旧 Tool 记录和旧样本。
旧单工具记录的步骤预算保持原规则；新配方建议最多两个工具项、24 个步骤，使用固定模板：父级前置/收尾 2 步，每项选择或 no-op 1 步、安装至多 4 步、绑定至多 4 步、补偿与终态重扫各 1 步。必要清理使用预留节点，禁止无限追加或内部重试；签发、push、persist、read 和 recover 必须一致校验预算，超过预算拒绝。
记录数量和总文件大小继续有界，不能简单放宽旧读取器的 `steps <= 8` 条件。旧 v1 缺省工具仅兼容 Node；新 Recipe 记录必须有严格 subject，非法新格式不能降级成旧单工具记录读取。
父记录需在首个变更前可靠落盘；成功标记须晚于实际解析核对，任务标签与终态不能默认归为 Node 安装。

新配方失败不自动降级到旧整机预设安装。此前成功项如果后来被外部改变，重试应提示另行核对，不能借旧完成状态获得新写权限。
